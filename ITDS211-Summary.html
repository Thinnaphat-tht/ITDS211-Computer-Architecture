1.3 Eight Great Ideas in Computer Architecture

  1. Design for Moore's Law — ออกแบบโดยคาดว่าทรานซิสเตอร์เพิ่มขึ้นเรื่อย ๆ
  2. Use abstraction to simplify design — ซ่อนรายละเอียดเป็นชั้น ๆ
  3. Make the common case fast — ทำเคสที่เกิดบ่อยให้เร็ว
  4. Performance via parallelism — ทำหลายอย่างพร้อมกัน
  5. Performance via pipelining — ทำเป็นสายพาน (ซ้อนขั้นตอน)
  6. Performance via prediction — เดาล่วงหน้า (เช่น branch prediction) ถ้าเดาถูกคุ้มกว่ารอ
  7. Hierarchy of memories — หน่วยความจำเป็นลำดับชั้น เร็ว/เล็ก/แพง → ช้า/ใหญ่/ถูก
  8. Dependability via redundancy — ทนทานโดยมีของสำรอง

1.4 Below Your Program

ชั้นของซอฟต์แวร์ (จากนอกเข้าใน): Application software → System software → Hardware

  • Application software — เขียนด้วย high-level language
  • System software — Compiler แปล HLL เป็น machine code; Operating System ให้บริการ: จัดการ input/output, จัดการ memory และ storage, จัด schedule งานและแชร์ทรัพยากร
  • Hardware — processor, memory, I/O controllers

Levels of Program Code

  1. High-level language (เช่น C) — ใกล้โจทย์ ผลิตภาพดี พกพาข้ามเครื่องได้ ↓ Compiler
  2. Assembly language — ข้อความแทนคำสั่ง (ตัวอย่างในสไลด์เป็น RISC-V: slli, add, ld, sd, jalr) ↓ Assembler
  3. Machine language — เลขฐานสอง (bits) เข้ารหัส instruction และ data

1.8 Performance — สูตรที่ต้องจำ

Performance = 1 / Execution Time
"X เร็วกว่า Y n เท่า" ⇒ PerformanceX / PerformanceY = ExecTimeY / ExecTimeX = n

ตัวอย่าง: A ใช้ 10s, B ใช้ 15s → ExecTimeB/ExecTimeA = 15/10 = 1.5 → A เร็วกว่า B 1.5 เท่า

วัด Execution Time

  • Elapsed time (wall-clock) — เวลาตอบสนองรวมทุกอย่าง: processing, I/O, OS overhead, idle → ตัวกำหนดประสิทธิภาพระบบ
  • CPU time — เวลาที่ CPU ประมวลผลงานนั้นจริง ๆ ไม่นับ I/O และงานอื่น; แบ่งเป็น user CPU time + system CPU time

Clock

  • Clock period = ระยะเวลา 1 cycle เช่น 250 ps = 0.25 ns = 250×10−12 s
  • Clock frequency (rate) = cycles ต่อวินาที เช่น 4.0 GHz = 4000 MHz = 4.0×109 Hz
  • Rate = 1 / Period
CPU Time = CPU Clock Cycles × Clock Cycle Time = CPU Clock Cycles / Clock Rate

ปรับปรุง performance ได้โดย ลดจำนวน clock cycles หรือ เพิ่ม clock rate (ผู้ออกแบบมักต้อง trade-off ระหว่าง clock rate กับจำนวน cycle)

Instruction Count และ CPI

Clock Cycles = Instruction Count × CPI (Cycles Per Instruction)
CPU Time = Instruction Count × CPI × Clock Cycle Time = (Instruction Count × CPI) / Clock Rate
  • Instruction Count ขึ้นกับ program, ISA และ compiler
  • CPI ขึ้นกับ hardware ของ CPU; ถ้าแต่ละ instruction มี CPI ต่างกัน ใช้ average CPI ซึ่งขึ้นกับ instruction mix

ตัวอย่างที่ 1: CPU Time

Computer A: 2 GHz, CPU time 10 s · Computer B ต้องการ 6 s แต่มี clock cycles มากกว่า A 1.2 เท่า → B ต้อง clock rate เท่าไร?
Clock CyclesA = 10 s × 2 GHz = 20×109
Clock RateB = (1.2 × 20×109) / 6 s = 24×109 / 6 = 4 GHz

ตัวอย่างที่ 2: CPI (ISA เดียวกัน)

A: cycle time 250 ps, CPI 2.0 · B: cycle time 500 ps, CPI 1.2 · ใครเร็วกว่า?
CPU TimeA = I × 2.0 × 250 = I × 500 ps
CPU TimeB = I × 1.2 × 500 = I × 600 ps
B/A = 600/500 = 1.2 → A เร็วกว่า B 1.2 เท่า
เทคนิคทำโจทย์: เขียน CPU Time = IC × CPI × T ของแต่ละเครื่องก่อน เมื่อ IC เท่ากันตัดทิ้งได้ แล้วหารเปรียบเทียบ — เครื่องที่มี CPI ต่ำกว่าไม่ได้เร็วกว่าเสมอ ต้องดู clock ด้วย

2.3 Hardware vs Software approach

  • (a) Programming in hardware — ลำดับฟังก์ชันคำนวณ/ตรรกะถูก "เดินสาย" ตายตัว เปลี่ยนงานต้องเดินสายใหม่
  • (b) Programming in software — ส่วนหนึ่งของ hardware (instruction interpreter) แปลรหัสคำสั่ง แล้วสร้าง control signals ให้หน่วยคำนวณอเนกประสงค์ → เปลี่ยนงานแค่ใส่ชุดรหัสใหม่ ไม่ต้องรื้อ hardware

องค์ประกอบหลัก: CPU (instruction interpreter + general-purpose arithmetic/logic functions + I/O components) พร้อมวิธีรับข้อมูลเข้าและรายงานผล

ขั้นตอนเมื่อมี interrupt

  • เพิ่ม Interrupt step ต่อท้าย cycle: หลัง execute ตรวจว่ามี interrupt ไหม → ถ้ามี ไปทำ ISR (Interrupt Service Routine) แล้วกลับมาทำต่อ
  • ระหว่างทำ interrupt ระบบทั่วไปมัก ปิด interrupt (ตั้ง bit ใน flags register) — interrupt ที่ถูกเมินแบบนี้คือ maskable
  • Nonmaskable = ต้องจัดการเสมอเพื่อให้ระบบเสถียร
  • Interrupt เหมาะกับ I/O; แต่ MARIE ใช้ programmed I/O แบบปรับ: ผลลัพธ์ใส่ OutREG และ CPU polling InREG จนมีข้อมูลก็คัดลอกเข้า AC

Timing กับ I/O และ Multiple interrupts

  • Short I/O wait — การรอ I/O สั้น CPU รอไม่เสียมาก; Long I/O wait — รอนาน ถ้าไม่มี interrupt CPU ว่างเปล่า ถ้ามี interrupt CPU ไปทำงานอื่นระหว่างรอได้ → ใช้ CPU คุ้มกว่า
  • Multiple interrupts: จัดการได้ 2 วิธี — (1) ปิด interrupt ระหว่างทำ ISR (เรียงตามลำดับที่มา) (2) ใช้ priority ให้ interrupt สำคัญกว่า ขัดจังหวะ ISR ที่ต่ำกว่าได้ (nested)
  • ตัวอย่างสไลด์: printer (t=10), communication (t=15), disk (t=25) ขัดผ่านโปรแกรมผู้ใช้ — ตัวที่ priority สูงกว่าแทรกเข้าไปก่อน
จำ: Interrupt ≠ ทำให้ cycle เสีย แต่เพิ่ม step "check interrupt" · Maskable = ปิดได้ · Nonmaskable = ปิดไม่ได้ · 4 class: Program, Timer, I/O, Hardware failure

A2 Sign & Magnitude (S&M)

  • บิตซ้ายสุด = sign bit S: 0 = บวก (หรือศูนย์), 1 = ลบ (หรือศูนย์); ที่เหลือ n บิตเป็น magnitude
  • ช่วงค่า: −(2n−1) ถึง +(2n−1) (n = จำนวนบิต magnitude)
  • ตัวอย่าง 8 บิต: 0000 0000 = +0, 1000 0000 = −0 → ศูนย์ไม่ unique (มี 2 ค่า); 8 บิตมีช่วง −127 ถึง +127

A3 Complement Method

เลข m ฐาน r มี n หลัก
(r−1)'s complement = (rn − 1) − m
r's complement = (rn − 1) − m + 1 = rn − m

ตัวอย่างฐาน 10: n = 3, m = 382 → 9's complement (−382) = 617 · 10's complement = 618

1's complement (ฐาน 2)

  • คำนวณ (2n−1) − m = กลับทุกบิต (invert)
  • m = 0101 (4 บิต) → 1010 = −5 ใน 1's complement
  • m = 00101011 → 11010100 · m = 00000000 (= 0) → 11111111 (= −0)
  • ช่วง 8 บิต: −127 ถึง +127 · มี สองศูนย์ (+0, −0)
  • การบวก: ถ้าผลมี carry ออกมา ให้ นำ carry ไปบวกที่ LSB (end-around carry)
6 + (−3) บน 3 บิต: 6 = 110, −3 = 100 (1's compl ของ 011)
110 + 100 = 1 010 → carry 1 → 010 + 1 = 011 = 3 ✔

2's complement

  • ไม่ต้องทำ end-around carry · สร้างโดย หา 1's complement แล้ว +1 ที่ LSB
  • ช่วง 8 บิต: −128 ถึง +127 (−128 เพราะมีการ +1 ให้ค่าลบ) · มีศูนย์ตัวเดียว
  • Short-cut: เริ่มจาก LSB หาบิต 1 ตัวแรก → คงบิตนั้นและบิตขวาไว้ แล้ว กลับ (invert) ทุกบิตทางซ้าย
หา 2's complement ของ 0101011: invert = 1010100, +1 = 1010101
6 + (−5) บน 4 บิต: 5 = 0101, −5 = 1011 → 0110 + 1011 = 1 0001 → ทิ้ง (discard) carry ออก → 0001 = 1 ✔

B1 RISC-V — พื้นฐาน

4.4 Block size, Misses & Write policy

Block Size

  • block ใหญ่ → miss rate ลด (spatial locality) แต่ ใน cache ขนาดคงที่ block ใหญ่ = จำนวนน้อยลง → แย่งกัน miss rate เพิ่ม + pollution + miss penalty สูงขึ้น
  • บรรเทาด้วย early restart และ critical-word-first

Cache miss

  • hit → CPU ทำงานต่อปกติ
  • miss → stall pipeline → ดึง block จาก level ถัดไป · I-cache miss: restart instruction fetch · D-cache miss: ทำ data access ให้เสร็จ

4.5 Measuring Cache Performance

CPU time = (Program execution cycles + Memory stall cycles) × Clock cycle time
Memory stall cycles = Memory accesses/Program × Miss rate × Miss penalty
   = Instructions/Program × Misses/Instruction × Miss penalty
AMAT = Hit time + Miss rate × Miss penalty
ตัวอย่าง CPI: I-miss 2%, D-miss 4%, miss penalty 100 cycle, base CPI 2, load/store 36%
I-cache: 0.02 × 100 = 2 · D-cache: 0.36 × 0.04 × 100 = 1.44
Actual CPI = 2 + 2 + 1.44 = 5.44 → ideal cache เร็วกว่า 5.44/2 = 2.72 เท่า
ตัวอย่าง AMAT: clock 1 ns, hit time 1 cycle, miss penalty 20 cycle, miss rate 5% → AMAT = 1 + 0.05×20 = 2 ns (= 2 cycle)

สรุป: เมื่อ CPU เร็วขึ้น (base CPI ลด หรือ clock เร็วขึ้น) miss penalty ยิ่งมีน้ำหนัก สัดส่วนเวลาใน memory stall มากขึ้น → ประเมินระบบโดยไม่ดู cache ไม่ได้

4.7 Multilevel Caches

  • Primary (L1) ติด CPU เล็กแต่เร็ว → เน้น minimal hit time
  • L2 รับ miss ของ L1 ใหญ่กว่า ช้ากว่า แต่เร็วกว่า main memory → เน้น low miss rate (hit time ผลน้อยกว่า)
  • Main memory รับ miss ของ L2 · ระบบบางตัวมี L3
  • ผลลัพธ์: L1 มักเล็กกว่า cache เดี่ยว และ L1 block size เล็กกว่า L2 block size
CPU base CPI = 1, 4 GHz (0.25 ns/cycle), miss rate 2%/instruction, main memory 100 ns
L1 อย่างเดียว: penalty = 100/0.25 = 400 cycle → CPI = 1 + 0.02×400 = 9
เพิ่ม L2 (access 5 ns, global miss rate ไป memory 0.5%): L1 miss + L2 hit penalty = 5/0.25 = 20 cycle · L1+L2 miss เพิ่ม 400 cycle (สไลด์ใช้ "extra 500")
CPI = 1 + 0.02×20 + 0.005×400 = 3.4 → เร็วขึ้น 9/3.4 ≈ 2.6 เท่า

CPU ขั้นสูง & Software

  • Out-of-order CPU ทำคำสั่งอื่นต่อระหว่าง cache miss (store ค้างใน load/store unit, dependent instruction รอใน reservation station) → วิเคราะห์ยาก ต้องใช้ simulation
  • miss ขึ้นกับรูปแบบการเข้าถึง memory (algorithm, compiler)
  • Software optimization via blocking (DGEMM): แบ่งเมทริกซ์เป็น block (เช่น BLOCKSIZE 32) เพื่อ ใช้ข้อมูลให้มากที่สุดก่อนถูกแทนที่ — loop 3 ชั้นนอก (sj, si, sk) เรียก do_block ที่ทำคูณเฉพาะ block ย่อย

4.8 Dependable Memory Hierarchy

  • Fault = component ล้มเหลว (อาจหรือไม่นำไปสู่ system failure)
  • สถานะ: Service accomplishment (บริการตามระบุ) ⇄ Service interruption (เบี่ยงเบน) — Failure → Restoration
MTTF (mean time to failure) = reliability · MTTR (mean time to repair)
MTBF = MTTF + MTTR · Availability = MTTF / (MTTF + MTTR)

เพิ่ม availability: เพิ่ม MTTF (fault avoidance, fault tolerance, fault forecasting) หรือลด MTTR (เครื่องมือ/กระบวนการวินิจฉัยซ่อมที่ดีขึ้น)

Hamming SEC code

  • Hamming distance = จำนวนบิตที่ต่างกันระหว่างสอง bit pattern
  • distance ต่ำสุด 2 → ตรวจจับ error 1 บิต (เช่น parity code) · distance 3 → แก้ error 1 บิต (SEC) และตรวจจับ 2 บิต
  • Encoding: นับบิตจาก 1 ทางซ้าย · ตำแหน่งที่เป็นกำลังของ 2 = parity bit (1, 2, 4, 8, …) · แต่ละ parity bit ตรวจ data bit บางตำแหน่ง
  • Decoding: ค่า parity bits บอกว่าบิตไหนผิด — 0000 = ไม่มี error · 1010 = บิต 10 พลิก

4.9 Virtual Machines

  • Host จำลอง guest OS และทรัพยากรเครื่อง · แยก (isolation) ดีขึ้น หลีกเลี่ยงปัญหา security/reliability · ช่วยแชร์ทรัพยากร · มี performance impact บ้าง · ตัวอย่าง: IBM VM/370 (ยุค 1970), VMware, Microsoft Virtual PC
  • VMM (Virtual Machine Monitor): map virtual resource → physical (memory, I/O, CPU); guest code รันบนเครื่องจริงใน user mode, trap ไป VMM เมื่อใช้ privileged instruction หรือเข้าถึงทรัพยากรที่ป้องกัน; guest OS ต่างจาก host ได้; VMM จัดการ I/O จริงและจำลอง virtual I/O
  • ตัวอย่าง Timer: เครื่องจริง OS ระงับ process → handle → เลือก process ถัดไป · มี VMM: VMM ระงับ VM → handle → เลือก VM ถัดไป; ถ้า VM ต้องการ timer → VMM จำลอง virtual timer และสร้าง interrupt ให้ VM เมื่อ timer จริงเกิด
  • Instruction set support: มี user mode / system mode; privileged instruction ใช้ได้ใน system mode เท่านั้น (ใน user mode → trap) · ทรัพยากรกายภาพทั้งหมด (page table, interrupt control, I/O register) เข้าถึงผ่าน privileged instruction

4.10 Virtual Memory, Page Table, TLB

Virtual memory = ใช้ main memory เป็น "cache" ของ secondary storage (disk) · จัดการร่วมกันโดย CPU hardware + OS · แต่ละโปรแกรมมี private virtual address space และถูกป้องกันจากกัน · CPU/OS แปล virtual → physical address
VM "block" = page · VM translation "miss" = page fault
  • Address translation แบ่งเป็น page ขนาดคงที่ (เช่น 4 KB)
  • Page fault penalty: ต้องดึง page จาก disk — ใช้เวลา หลายล้าน clock cycle · OS จัดการ · ลด page fault rate ด้วย fully associative placement และ replacement algorithm ฉลาด

Page table

  • เก็บข้อมูล placement · เป็น array ของ PTE (page table entry) ที่ index ด้วย virtual page number · page table register ใน CPU ชี้ page table ใน physical memory
  • page อยู่ใน memory → PTE เก็บ physical page number + status bits (reference, dirty, …) · ไม่อยู่ → PTE ชี้ตำแหน่งใน swap space บน disk

Replacement & writes

  • ใช้ LRU เพื่อลด page fault: reference bit (use bit) ใน PTE ตั้งเป็น 1 เมื่อเข้าถึง page; OS เคลียร์เป็น 0 เป็นระยะ — reference bit = 0 แปลว่าไม่ได้ใช้เร็ว ๆ นี้
  • เขียน disk ช้าหลายล้าน cycle → เขียนทั้ง block ครั้งเดียว; write-through ไม่เหมาะ → ใช้ write-back พร้อม dirty bit ใน PTE

TLB (Translation Look-aside Buffer)

  • ปัญหา: translation ต้องอ้าง memory เพิ่ม (1 ครั้งเพื่ออ่าน PTE + 1 ครั้งสำหรับ access จริง) แต่ page table มี locality ดี → ใช้ cache ของ PTE ใน CPU = TLB
  • ทั่วไป: 16–512 PTEs, hit 0.5–1 cycle, miss 10–100 cycle, miss rate 0.01%–1% · miss จัดการได้ทั้ง hardware หรือ software
กรณีการจัดการ
TLB miss แต่ page อยู่ใน memoryโหลด PTE จาก memory แล้ว retry (hardware หรือ software exception handler) · ต้องรู้ว่า TLB miss ก่อน destination register ถูกเขียนทับ → raise exception → handler copy PTE เข้า TLB → restart instruction
Page fault (page ไม่อยู่ใน memory)OS: ① ใช้ faulting virtual address หา PTE ② หา page บน disk ③ เลือก page จะถูกแทนที่ (ถ้า dirty เขียนลง disk ก่อน) ④ อ่าน page เข้า memory + อัปเดต page table ⑤ ทำ process ให้ runnable ⑥ restart จาก instruction ที่ fault

TLB & Cache interaction / Protection

  • cache tag ใช้ physical address → ต้องแปลก่อน lookup; ทางเลือก virtual address tag มีปัญหา aliasing (virtual address ต่างกันชี้ physical เดียวกัน)
  • Memory protection: task แชร์ virtual space บางส่วนได้ แต่ต้องกันการเข้าถึงผิดพลาด — ต้องมี OS ช่วย และ hardware: supervisor (kernel) mode, privileged instructions, page table เข้าถึงได้เฉพาะ supervisor mode, system call exception (เช่น ecall ใน RISC-V)

4.12 Cache Control FSM & Cache Coherence

Simple cache + FSM

  • ตัวอย่าง: direct-mapped, write-back, write allocate · block 4 words (16 B) · cache 16 KB (1024 blocks) · address 32 บิต · valid bit และ dirty bit ต่อ block · blocking cache (CPU รอจนจบ)

  • สัญญาณ CPU ↔ Cache: Read/Write, Valid, Address (32), Write Data (32), Read Data (32), Ready · Cache ↔ Memory: Address 32, data 128 บิต (หลายรอบต่อ access)
  • FSM: ชุด state เปลี่ยนที่ clock edge; Next state = fn(current state, inputs); Control outputs = fo(current state) · state เก็บใน register

Cache Coherence

ปัญหา: 2 core แชร์ physical address space แต่ cache แยก (เช่น write-through) → CPU A เขียน X=1 แต่ cache ของ CPU B ยังเป็น 0

Coherence (ไม่เป็นทางการ): read ต้องคืนค่าที่เขียนล่าสุด
เป็นทางการ: ① P เขียน X แล้วอ่าน X (ไม่มีใครเขียนคั่น) → ได้ค่าที่เขียน ② P1 เขียน X, P2 อ่าน X (ห่างพอ) → ได้ค่าที่เขียน ③ P1, P2 เขียน X → ทุก processor เห็นลำดับการเขียนเหมือนกัน (ค่าสุดท้ายเดียวกัน)
  • Protocol: migration (ย้ายข้อมูลมา cache ท้องถิ่น ลดภาระ shared memory) + replication (สำเนา read-shared ลดการแย่ง)
  • Snooping — ทุก cache คอยดู bus read/write · Directory-based — cache และ memory บันทึกสถานะแชร์ของ block ใน directory
  • Invalidating snooping: cache ขอสิทธิ์ exclusive ก่อนเขียน → broadcast invalidate บน bus → read ถัดไปใน cache อื่น miss → cache เจ้าของส่งค่าใหม่ให้
  • Memory consistency: write ถือว่าสำเร็จเมื่อทุก processor เห็น; processor ไม่จัดลำดับ write ใหม่ → ถ้า P เขียน X แล้ว Y ใครเห็น Y ใหม่ต้องเห็น X ใหม่ด้วย · อ่านจัดลำดับใหม่ได้ แต่เขียนไม่ได้

ตัวอย่างจริง: ARM Cortex-A53 & Intel Core i7

  • cache หลายระดับบนชิป, 2-level TLB, multi-banked cache (เข้าถึงหลายครั้ง/cycle ถ้าไม่ชน bank)
  • optimization: return requested word first, non-blocking cache (hit under miss, miss under miss), data prefetching

RISC-V system instructions: memory ordering (fence.i, fence, sfence.vm) · CSR access (csrrw/rs/rc และแบบ immediate) · system (ecall, ebreak, sret, wfi)

4.13 Pitfalls & Concluding Remarks

  • Byte vs word addressing: cache 32 byte direct-mapped, block 4 byte → byte 36 ไป block 1 แต่ word 36 ไป block 4
  • เขียนโค้ดโดยไม่สนใจ memory system (เช่น วน row vs column ของ array — stride ใหญ่ = locality แย่)
  • multiprocessor ที่แชร์ L2/L3: associativity น้อยกว่าจำนวน core → conflict miss; core มากขึ้นต้องเพิ่ม associativity
  • ใช้ AMAT ประเมิน out-of-order CPU ไม่ได้ (ไม่รวม non-blocked accesses) → ใช้ simulation
  • ขยาย address ด้วย segment (Intel 80286) — segment ไม่พอ ทำให้คำนวณ address ซับซ้อน
  • ทำ VMM บน ISA ที่ไม่ได้ออกแบบสำหรับ virtualization (non-privileged instruction เข้าถึง hardware) → ต้องขยาย ISA หรือห้าม guest OS ใช้คำสั่งเหล่านั้น
สรุปบท: memory เร็ว = เล็ก, memory ใหญ่ = ช้า → caching ให้ภาพลวงว่าเร็วและใหญ่ ด้วย principle of locality · hierarchy: L1 → L2 → … → DRAM → disk · memory system สำคัญมากต่อ multiprocessor

การรับ block ข้อมูล 3 เทคนิค: Programmed = CPU loop อ่าน status ซ้ำ ๆ แล้วถ่ายทีละ word · Interrupt = CPU ทำงานอื่น ถูกขัดจังหวะทุก word · DMA = CPU สั่งเริ่มแล้วไปทำอย่างอื่น ถูก interrupt เมื่อเสร็จทั้ง block

5.4 Interrupt-Driven I/O

Simple interrupt processing

  1. I/O module ส่งสัญญาณ interrupt
  2. CPU ทำคำสั่งปัจจุบันจนเสร็จ
  3. CPU เก็บ PC และ PSW (Status register) ลง stack ก่อน
  4. เริ่มทำงานที่ ISR (Interrupt Service Routine)
  5. เสร็จแล้ว restore PC/PSW กลับไปทำโปรแกรมเดิม

Design issues 2 ข้อ

  1. มี I/O module หลายตัว — CPU รู้ได้อย่างไรว่าอุปกรณ์ไหนเป็นผู้ interrupt?
  2. ถ้ามีหลาย interrupt พร้อมกัน — CPU เลือกทำตัวไหนก่อน?

5.5 DMA (Direct Memory Access)

  • ใช้ DMA controller ถ่ายข้อมูลระหว่าง I/O กับ memory โดยตรง · CPU เพียง เริ่มต้นและรับ interrupt ตอนจบ
  • DMA ขอใช้ system bus; จุดที่ processor หยุดตรวจคำขอ: DMA แทรกได้เร็วและถี่กว่า (เกี่ยวกับ hardware bus ตรง ๆ แทรกได้ในหลาย จุดของ instruction cycle) · Interrupt ต้องรอจน instruction ปัจจุบันเสร็จ
  • ตัวอย่างชิป: Intel 8237A มี register: Command, Status (channel 0–3 reached TC = terminal count), Mode (verify/write/read transfer, auto-init, address increment/decrement, demand/single/block/cascade), Single Mask, All Mask
  • Alternative DMA configurations: DMA module แยกบน bus / เชื่อมหลาย I/O ผ่าน DMA เดียว / I/O bus แยก — ลดจำนวนการใช้ system bus
เปรียบเทียบสามเทคนิค (จุดที่ข้อสอบชอบ): CPU ว่างระหว่าง I/O? Programmed ✗, Interrupt ✔ (แต่ถูกขัดบ่อย), DMA ✔ · ใครถ่ายข้อมูล? Programmed/Interrupt → CPU, DMA → DMA controller · interrupt ถี่แค่ไหน: Interrupt-driven ทุก word / DMA ครั้งเดียวต่อ block

5.6 Direct Cache Access (DCA)

  • ปัญหา: DMA ไม่ scale พอเมื่อ data rate เพิ่มมาก — Ethernet 10/100 Gbps ที่ database server, Wi-Fi ระดับ Gbps (3.2 และ 6.76 Gbps)
  • Network traffic เป็น packet (protocol data unit): link level ปกติ Ethernet โดยมี IP และ TCP ซ้อนอยู่ใน payload · ขาออก packet ถูกสร้างที่ NIC/I/O controller · ขาเข้า controller ลอก Ethernet header ส่ง TCP/IP packet ให้ host CPU
  • ทั้งขาเข้า-ขาออก core, main memory และ cache ล้วนเกี่ยวข้อง: แอปวางข้อมูลใน application buffer → core ย้ายไป system buffer สร้าง TCP/IP header → DMA ดึงไปส่งที่ NIC
ขาเข้า (Incoming)ขาออก (Outgoing)

DCA strategies

  • ได้ผลมากกว่าถ้าตัด system buffer ใน main memory ทิ้ง — core เข้าถึง packet/descriptor ใน system buffer แค่ครั้งเดียว (อ่านแล้วย้าย payload ไป application buffer)
  • วิธีง่ายสุด (prototype บน Xeon ปี 2006–2010): DCA ใช้ได้เฉพาะ incoming network traffic · DCA function อยู่ใน memory controller ส่ง prefetch hint ให้ core ทันทีที่ข้อมูลอยู่ใน system memory → core prefetch data packet จาก system buffer
  • Cache injection = วางข้อมูลลง cache โดยตรง — ใน Intel Xeon เรียก Direct Data I/O (DDIO)

5.7 Evolution of the I/O Function (6 ขั้น)

  1. CPU ควบคุมอุปกรณ์ต่อพ่วงโดยตรง
  2. เพิ่ม controller/I/O module — CPU ใช้ programmed I/O ไม่มี interrupt
  3. เหมือนข้อ 2 แต่ใช้ interrupt — CPU ไม่ต้องรอ I/O เสร็จ ประสิทธิภาพเพิ่ม
  4. I/O module มี DMA เข้าถึง memory ตรง — ย้ายข้อมูลทั้ง block โดย CPU เกี่ยวข้องเฉพาะตอนเริ่มและจบ
  5. I/O module พัฒนาเป็น processor ในตัวเอง มี instruction set เฉพาะ I/O (I/O channel)
  6. I/O module มี local memory เป็นคอมพิวเตอร์ในตัวเอง (I/O processor) — ควบคุมอุปกรณ์จำนวนมากด้วย CPU ยุ่งน้อยที่สุด

6.3 Disk Performance Parameters

ดิสก์หมุนด้วยความเร็วคงที่; ก่อนอ่าน/เขียน head ต้องไปที่ track ที่ต้องการ แล้วรอให้ sector หมุนมาตรงหัว

Seek time (Ts) = เวลาเคลื่อน head ไปยัง track (movable-head)
Rotational delay / latency = เวลาที่ต้นของ sector หมุนมาถึง head · เฉลี่ย = ครึ่งรอบ = ½ ÷ (rpm/60)
Access time = Seek time + Rotational delay (เวลาเข้าตำแหน่ง)
Transfer time = เวลาอ่าน/เขียนเมื่อ sector ผ่านใต้ head (= ขนาดข้อมูล ÷ transfer rate)
รวมต่อครั้ง = Seek + Rotational latency + Transfer (+ controller overhead, queuing)

6.4 RAID (Redundant Array of Independent Disks)

เทคนิคนำ HDD หลายตัวมารวมทำงานเป็นกลุ่มเดียว มี 7 ระดับ (0–6) — ระดับ ไม่ได้ซ้อนเป็นลำดับชั้น แต่เป็นสถาปัตยกรรมต่างกัน ที่มี 3 คุณสมบัติร่วม:

  1. ชุด physical disk หลายตัว OS มองเป็น logical drive เดียว
  2. ข้อมูลถูกกระจายข้าม disk ใน array ด้วย striping
  3. ใช้ความจุส่วนเกินเก็บ parity เพื่อ กู้ข้อมูล เมื่อ disk เสีย

7.1 Pipelining Overview

Pipelining Analogy (ซักผ้า): ซักผ้า 4 ชุด ถ้าทำทีละชุดต่อเนื่องจบ ใช้ 8 ชั่วโมง; ถ้า ซ้อนการทำงาน (overlap) ใช้ 3.5 ชั่วโมง → Speedup = 8/3.5 ≈ 2.3
กรณี non-stop (n ชุดมาก ๆ): Speedup = 2n / (0.5n + 1.5) ≈ 4 = จำนวน stage

RISC-V pipeline 5 stage — "ทำ 1 ขั้นต่อ 1 stage"

Stageทำอะไร
IF Instruction Fetchดึง instruction จาก memory
ID Instruction Decodeถอดรหัส + อ่าน register
EX Executeทำ operation หรือ คำนวณ address
MEM Memory accessเข้าถึง memory operand
WB Write Backเขียนผลกลับ register
The BIG Picture: pipelining เพิ่ม performance โดยเพิ่ม instruction throughput (ทำหลายคำสั่งขนานกัน) · แต่ latency ของแต่ละ instruction เท่าเดิม · ติดข้อจำกัดเรื่อง hazards (structure, data, control) · การออกแบบ ISA มีผลต่อความซับซ้อนของ pipeline

  • instruction ยาว 32 บิตเท่ากันทุกตัว → fetch/decode ง่ายใน 1 cycle (เทียบ x86: ยาว 1–17 byte)
  • format น้อยและสม่ำเสมอ → decode และอ่าน register ได้ในขั้นเดียว
  • Load/store addressing: คำนวณ address ใน stage 3 (EX) แล้วเข้าถึง memory ใน stage 4 (MEM)

7.6 Load-Use Hazard Detection & Stalling

  • ตรวจใน ID stage ตอนถอดรหัสคำสั่งที่ใช้ค่า: operand คือ IF/ID.RegisterRs1, IF/ID.RegisterRs2
  • Load-use hazard เมื่อ: ID/EX.MemRead และ (ID/EX.RegisterRd = IF/ID.RegisterRs1 หรือ = IF/ID.RegisterRs2) (สไลด์พิมพ์ Rs1 ซ้ำสองครั้ง — ตัวที่สองควรเป็น Rs2)
  • ถ้าตรวจพบ: stall และสอด bubble

วิธี stall pipeline

  1. บังคับค่าควบคุมใน ID/EX register เป็น 0 → EX, MEM, WB ทำ nop (no-operation)
  2. ห้ามอัปเดต PC และ IF/ID register → คำสั่งที่ใช้ค่าถูก decode ซ้ำ และคำสั่งถัดไปถูก fetch ซ้ำ
  3. stall 1 cycle ให้ MEM อ่านข้อมูลของ ld ได้ แล้วจึง forward เข้า EX ได้
Stalls ลด performance แต่จำเป็นเพื่อ ผลลัพธ์ถูกต้อง · compiler จัดโค้ดเลี่ยง hazard/stall ได้ — ต้องรู้โครงสร้าง pipeline

7.7 Control Hazards & Branch Prediction

Branch hazard

  • ถ้ารู้ผล branch ที่ MEM stage: คำสั่งที่ fetch ผิดไปแล้ว (3 คำสั่ง) ต้อง flush (ตั้งค่า control เป็น 0)
  • Reducing branch delay: ย้าย hardware ตัดสินผลมาที่ ID stage — เพิ่ม target address adder + register comparator
Branch taken: 36: sub x10,x4,x8 · 40: beq x1,x3,16 // PC-relative → target = 40 + 16×2 = 72 · 44: and · 48: orr · 52: add · 56: sub … · 72: ld x4,50(x7)
เมื่อ taken: คำสั่งที่ 44 ถูก flush แล้ว fetch จาก 72 (เสีย 1 cycle เมื่อตัดสินใน ID)

Branch prediction

  • pipeline ยาวขึ้นรู้ผลเร็วไม่ได้ → stall penalty รับไม่ได้ → ทำนายผล branch และ stall เฉพาะเมื่อ ทำนายผิด
  • RISC-V pipeline: ทำนายว่า ไม่ taken — fetch คำสั่งถัดไปได้เลยไม่เสียเวลา

Vector processors

  • function unit แบบ pipeline สูง · stream ข้อมูลจาก/ไป vector registers · ข้อมูลถูกเก็บจาก memory เข้า register และผลเก็บกลับ
  • ตัวอย่าง Vector extension ของ RISC-V: v0–v31 = 32 registers × 64 element (element 64 บิต) · fld.v / fsd.v load/store vector · fadd.d.v บวก vector double · fadd.d.vs บวก scalar เข้าทุก element · fmul.d.vs คูณ vector กับ scalar

// Conventional RISC-V                         // Vector RISC-V
fld   f0, a(x3)      // load scalar a            fld     f0, a(x3)
addi  x5, x19, 512   // end of array X           fld.v   v0, 0(x19)       // load vector x
loop: fld f1, 0(x19)                             fmul.d.vs v0, v0, f0     // vector-scalar multiply
      fmul.d f1, f1, f0                          fld.v   v1, 0(x20)       // load vector y
      fld f2, 0(x20)                             fadd.d.v v1, v1, v0      // vector-vector add
      fadd.d f2, f2, f1                          fsd.v   v1, 0(x20)       // store vector y
      fsd f2, 0(x20)
      addi x19,x19,8 ; addi x20,x20,8
      bltu x19,x5,loop
Conventional ใช้ loop 64 รอบ ~ 8 คำสั่งต่อรอบ; Vector ใช้ 6 คำสั่งเท่านั้น

Vector vs Scalar

8.4 Shared Memory & Multicore

  • SMP (Shared memory Multiprocessor): hardware ให้ single physical address space สำหรับทุก processor · sync ตัวแปรร่วมด้วย locks

Sum reduction: รวม 64,000 ตัวเลขบน 64 processor แบบ UMA (Pn = 0–63)
① แบ่ง ตัวเลข 1000 ตัวต่อ processor แล้วรวมส่วนของตัวเอง: sum[Pn]=0; for (i=1000*Pn; i<1000*(Pn+1); i+=1) sum[Pn] += A[i];
② Reduction แบบ divide and conquer: ครึ่งหนึ่งของ processor บวกคู่, แล้วเหลือ ¼, … ต้อง synchronize ทุกขั้น 
half = 64;
do {
  synch();
  if (half%2 != 0 && Pn == 0)
      sum[0] += sum[half-1];   // half เป็นเลขคี่ — P0 รับ element ที่ขาด
  half = half/2;
  if (Pn < half) sum[Pn] += sum[Pn+half];
} while (half > 1);
64 → 32 → 16 → 8 → 4 → 2 → 1 = 6 ขั้น

8.5 Introduction to GPUs

  • ประวัติ: video card ยุคแรก = frame buffer memory + address generation ส่งออกวิดีโอ → 3D graphics (เริ่มจากเครื่องระดับสูงเช่น SGI) → Moore's Law ทำให้ถูกลง ความหนาแน่นสูง → 3D graphics card ใน PC และ game console
  • GPU = Graphics Processing Unit: processor ที่มุ่งงาน 3D graphics: vertex/pixel processing, shading, texture mapping, rasterization

  • Heterogeneous CPU/GPU: CPU ทำโค้ด sequential, GPU ทำโค้ด parallel
